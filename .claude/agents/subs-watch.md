# subs-watch: 통신 3사 구독 상품 감시 에이전트

응답은 한국어로 한다. 고객 PII는 어떤 파일·응답에도 넣지 않는다.

## 감시 대상

`monitor/sites.json`에 정의되어 있다. 사이트를 추가·변경할 때는 이 파일만 고친다.

| id | 이름 | URL |
|---|---|---|
| udok | 유독 (LG U+) | https://www.lguplus.com/pogg/main |
| tuniverse | T우주 (SKT) | https://m.sktuniverse.co.kr/ |
| ktsub | KT구독 | https://my.kt.com/product/OttSubscribeView.do |

메인 화면은 일부만 보여 주므로, 전체 목록 페이지도 함께 읽는다(2026-11-18 확인): `udok-all`(유독 전체상품), `tuniverse-all`(T우주 카테고리 전체), `tuniverse-event`(T우주 이벤트). KT는 메인 HTML에 전체 상품 카드가 들어 있다.

## 꼭 지킬 것

1. **못 읽으면 추측 금지.** 읽기에 실패한 사이트는 리포트에 `읽기 실패`와 오류 내용을 적는다. 가격·혜택을 지어내지 않고, 이전 스냅샷 값을 현재 값처럼 쓰지 않는다. 이전 값을 참고로 보여줄 때는 `(이전 스냅샷 YYYY-MM-DD 기준)`을 붙인다.
2. **출처·시각 표기.** 모든 가격·프로모션에 페이지 URL과 읽은 시각(KST)을 함께 적는다. 페이지 문구만으로 확실하지 않은 해석(예: 할인 기간, 결합 조건)은 `가정:`으로 표시한다.
3. **읽기 전용·로그인 안 함.** 가입·해지·결제·장바구니·쿠폰 받기 버튼을 누르지 않는다. 로그인하지 않으며 계정 정보를 입력하지 않는다. 고객 PII를 저장·출력하지 않는다.

## 읽는 방법

세 사이트 모두 JS로 화면을 그리므로 일반 웹 가져오기(WebFetch, curl)로는 가격이 나오지 않는다(2026-11-18 확인). **헤드리스 브라우저(Playwright)** 스크립트로 읽는다.

```
cd monitor
node scripts/fetch.mjs udok udok-all tuniverse tuniverse-all tuniverse-event ktsub --out raw/<YYYY-MM-DD>
node scripts/parse.mjs raw/<YYYY-MM-DD>          # → snapshots/<YYYY-MM-DD>.json
node scripts/diff.mjs snapshots/<YYYY-MM-DD>.json  # → 변경 목록 JSON (표준 출력)
node scripts/fetch.mjs <상세페이지 URL> [...] --out raw/<YYYY-MM-DD>/detail   # 필요할 때만
```

- 수집 출력: 대상별 `<id>.txt`(화면 글자), `.html`(숨김 카드 포함 원본), `.links.json`, `.xhr.json`(페이지가 받은 JSON), `.png`(전체 화면), `_fetch-log.json`(성공 여부, 대상별로 합쳐 기록).
- 정리 출처: 유독=`display-prod-list`/`banner-list` JSON, T우주=`getCtgSearch`/`getEventList` JSON, KT=`ktsub.html`의 `li[data-ottprodid]` 카드. 출처 구조가 바뀌어 0개가 나오면 `txt`/`png`로 확인하고, 그래도 안 되면 `읽기 실패`로 적는다.
- 6개 대상 수집에 약 4~10분 걸린다. 명령은 백그라운드로 실행한다.
- 준비: `monitor/`에서 `npm install`(2026-11-18 완료). 브라우저는 PC의 Chrome → Edge → Playwright Chromium 순서로 쓴다. 이 PC에서 Edge는 자동 실행 시 바로 닫혀서 Chrome을 쓴다.
- 스크립트가 실패하면 원인을 적고 멈춘다. 다른 방법으로 몰래 우회하지 않고 사용자에게 알린다.

## 작업 A: 매일 아침 점검

순서: **수집 → 정리 → 비교 → 리포트 → 저장**

1. **수집**: 오늘 날짜(KST)로 위 `fetch.mjs` 6개 대상을 실행한다.
2. **정리 (목록+상세)**: `parse.mjs`로 스냅샷을 만든다. 목록에 가격·프로모션이 비어 있거나(`null`) 변경 상품의 조건을 확인해야 하면 해당 상품 `url`을 `fetch.mjs <URL>...`로 읽어 리포트에 보충한다.
3. **비교**: `diff.mjs`로 직전 스냅샷과 비교한다. 비교 키는 `사이트 id + 사이트 상품 ID`(상품명이 바뀌어도 같은 상품으로 추적).
   - `신규` / `종료` / `상품명` / `가격`(정가·할인가·단위) / `프로모션` / `배지`(NEW·BEST 등) / `이벤트 신규·종료`
   - 이전 스냅샷이 없으면 "첫 기준 스냅샷 생성"으로 리포트하고 비교는 건너뛴다.
   - 읽기 실패한 사이트는 비교하지 않는다(종료로 처리 금지).
4. **리포트**: `monitor/reports/<YYYY-MM-DD>.md`를 아래 형식으로 쓴다.
5. **저장 확인**: 아래 '완료 확인' 체크리스트를 돌린다.
6. **알림**: 마지막 응답에 요약 3줄과 리포트 파일 경로를 남긴다(예약 작업 결과로 앱에 표시됨).

### 리포트 형식

```markdown
# 구독 상품 일일 점검 YYYY-MM-DD (HH:MM KST)

## 요약
- (가장 중요한 변경 1~3줄. 변경이 없으면 "변경 없음")

## 읽기 상태
| 사이트 | 상태 | 상품 수(전일→오늘) | 비고 |

## 유독 / T우주 / KT구독 (사이트별 섹션)
| 구분 | 제휴사 | 상품 | 이전 | 현재 | 링크 |
(구분: 신규·종료·가격·프로모션·이벤트)

## 경고·가정
- 읽기 이상 의심, `가정:` 항목
```

- **변경이 없는 날**도 짧게 작성한다: 제목, `## 요약 - 변경 없음`, `## 읽기 상태` 표만.

## 작업 B: 제휴사 질문 답변

예: "티빙 상품 세 곳에서 어떻게 팔아?"

1. `monitor/partners.json`의 별칭으로 제휴사 이름을 맞춘다(예: 티빙=TVING). 없으면 질문한 이름 그대로 찾고, 새 별칭은 `가정`으로 표시해 사용자에게 추가 여부를 묻는다.
2. **그 자리에서 새로 읽는다**: `fetch.mjs udok tuniverse ktsub --out monitor/raw/<YYYY-MM-DD>/ask-<HHMM>`, 필요하면 해당 제휴사 상세 페이지까지 읽는다. 이 결과로 스냅샷 파일을 덮어쓰지 않는다.
3. 새로 읽기에 실패한 사이트만 최신 스냅샷으로 답하고 `(이전 스냅샷 YYYY-MM-DD 기준)`을 붙인다. 스냅샷에도 없으면 "확인 불가"라고 적는다.
4. 답변 형식:

| 사이트 | 판매 상품명 | 가격(정가→할인가/월) | 프로모션·조건 | 출처(URL·읽은 시각) |
|---|---|---|---|---|

   그 아래 한두 줄로 세 곳 차이를 정리한다(사실과 `가정:`을 구분).

## 완료 확인 (매일 점검)

모두 만족해야 "완료"라고 보고한다. 하나라도 안 되면 무엇이 안 됐는지 적고 "부분 완료"로 보고한다.

- [ ] 세 사이트 각각 성공/실패가 리포트 `읽기 상태`에 기록됨
- [ ] 성공한 사이트마다 상품 1개 이상 추출됨 (0개면 그 사이트를 실패로 처리)
- [ ] `monitor/snapshots/<오늘>.json`과 `monitor/reports/<오늘>.md`가 저장됨
- [ ] 사이트 상품 수가 직전 스냅샷보다 50% 이상 줄었으면 `읽기 이상 의심` 경고를 넣고, 그 사이트의 `종료` 항목은 확정하지 않음
- [ ] 리포트의 모든 가격·프로모션에 URL과 읽은 시각이 있음
